# Technical Specification

## 1. Назначение системы

Система представляет собой локальную multi-agent платформу для обучения студентов с использованием больших языковых моделей.

Основная задача системы — предоставлять персонализированную учебную помощь за счёт разделения функций между специализированными агентами.

Система должна работать локально и не требовать отправки учебных запросов во внешние LLM API.

---

## 2. Пользователь

Основным пользователем системы является студент.

Студент может:

* получать объяснения учебных понятий;
* получать учебные задания;
* отправлять свои ответы;
* получать оценку;
* получать объяснение ошибок;
* продолжать обучение с использованием предыдущей истории.

---

## 3. Функциональные требования

### FR-01. Объяснение учебных понятий

Система должна уметь объяснять учебные понятия простым и понятным языком.

Для этого используется **Tutor Agent**.

Пример:

```text
Объясни, что такое производная
```

Результатом является структурированное объяснение с примером и проверочным вопросом.

---

### FR-02. Генерация заданий

Система должна уметь генерировать учебные задания по указанной теме.

Для этого используется **Assessment Agent**.

Пример:

```text
Создай задачу по квадратным уравнениям
```

Агент должен сформировать понятное задание с указанием сложности.

---

### FR-03. Проверка ответа

Система должна уметь проверять ответ студента.

Пример:

```text
Проверь мой ответ.
Уравнение x² - 10x + 16 = 0.
Я получил x = 3 и x = 5.
```

Assessment Agent должен:

* определить корректность ответа;
* найти ошибки;
* предоставить объяснение;
* выставить оценку.

---

### FR-04. Обратная связь

Система должна предоставлять студенту actionable feedback.

Feedback должен содержать:

* описание ошибки;
* объяснение причины;
* рекомендации по улучшению.

---

### FR-05. Маршрутизация

Все пользовательские запросы должны проходить через центральный Orchestrator.

Orchestrator передаёт запрос Router, который выбирает специализированного агента.

```text
User
  ↓
Orchestrator
  ↓
Router
  ├── Tutor
  └── Assessment
```

---

## 4. Требования к агентам

### Tutor Agent

Tutor отвечает за:

* объяснение материала;
* работу с RAG;
* работу с memory;
* адаптацию объяснения под студента.

Tutor не является основным агентом для оценивания ответов.

---

### Assessment Agent

Assessment отвечает за:

* генерацию заданий;
* оценивание;
* анализ ошибок;
* feedback;
* сохранение результатов обучения.

---

## 5. Agent Skills

Поведение агентов должно определяться не только Python-кодом, но и декларативными skill-файлами.

Tutor:

```text
agents/tutor/skills/explain_concept.md
```

Assessment:

```text
agents/assessment/skills/generate_task.md
agents/assessment/skills/evaluate_answer.md
agents/assessment/skills/give_feedback.md
```

Дополнительно каждый агент имеет:

```text
SOUL.md
BEHAVIOR.md
RULES.md
```

---

## 6. Local LLM

Система должна использовать локальную open-source LLM через Ollama.

Основная модель:

```text
Gemma3:4b
```

Дополнительно были протестированы:

```text
Qwen3:4b
Llama3.2:3b
```

Выбор основной модели выполняется на основе benchmark.

---

## 7. Изоляция

Компоненты системы должны запускаться в изолированных Docker-контейнерах.

Минимальный набор сервисов:

```text
orchestrator
tutor
assessment
ollama
```

Docker Compose используется для конфигурации и сетевого взаимодействия сервисов.

---

## 8. Tools

Система должна поддерживать вызов внешних инструментов через единый Tool Registry.

Текущие инструменты:

```text
search_knowledge
solve_quadratic
```

### search_knowledge

Выполняет поиск информации в образовательной базе знаний.

### solve_quadratic

Решает квадратное уравнение:

```text
ax² + bx + c = 0
```

Возвращает:

* дискриминант;
* корни;
* количество корней.

При проверке математических ответов результат инструмента считается authoritative result.

---

## 9. RAG

Система должна поддерживать Retrieval-Augmented Generation.

Источник знаний:

```text
rag_data/
├── math.md
└── algebra.md
```

Для создания embeddings используется:

```text
all-MiniLM-L6-v2
```

Минимальный pipeline:

```text
Query
  ↓
Embedding
  ↓
Similarity search
  ↓
Relevant context
  ↓
LLM prompt
```

---

## 10. Memory

Система должна хранить информацию о процессе обучения студента.

Memory должна поддерживать:

### Short-term memory

Хранение истории текущей сессии.

Идентификаторы:

```text
student_id
session_id
```

### Long-term memory

Хранение:

```text
assessment history
learning progress
mistakes
student facts
```

Memory реализуется через SQLite.

Tutor и Assessment должны использовать общую базу памяти.

---

## 11. Персонализация

Система должна учитывать предыдущий опыт студента.

Пример:

```text
Assessment
    ↓
ошибка студента
    ↓
Shared Memory
    ↓
Tutor
    ↓
персонализированное объяснение
```

Это позволяет использовать предыдущие ошибки и результаты оценивания в последующих учебных запросах.

---

## 12. Observability

Система должна предоставлять возможность отслеживать работу LLM-системы.

Используется Langfuse.

Для запросов отслеживаются:

```text
input
output
model
latency
token usage
agent
student_id
session_id
```

---

## 13. Evaluation

Система должна быть протестирована на нескольких локальных моделях.

Используются:

```text
Qwen3:4b
Gemma3:4b
Llama3.2:3b
```

Минимальный benchmark включает:

```text
1. explain_derivative
2. generate_quadratic_task
3. evaluate_quadratic_answer
```

Для каждого запроса измеряется latency и анализируется корректность результата.

Результаты сохраняются в:

```text
eval_results.json
```

Подробное описание находится в:

```text
EVALUATION.md
```

---

## 14. API

### Orchestrator

```text
POST /handle
Port: 5000
```

Пример:

```json
{
  "input": "Объясни, что такое производная",
  "student_id": "ivan",
  "session_id": "session-1"
}
```

### Tutor

```text
POST /run
Port: 5001
```

### Assessment

```text
POST /run
Port: 5002
```

---

## 15. Нефункциональные требования

### NFR-01. Локальность

Обработка учебных запросов должна выполняться локально через Ollama.

### NFR-02. Изоляция

Компоненты системы должны запускаться в Docker-контейнерах.

### NFR-03. Расширяемость

Новые агенты и skills должны добавляться без необходимости полностью переписывать существующую архитектуру.

### NFR-04. Наблюдаемость

Работа системы должна быть доступна для анализа через Langfuse.

### NFR-05. Персистентность памяти

История обучения не должна зависеть от конкретного процесса агента.

---

## 16. Ограничения

Текущая минимальная версия системы имеет следующие ограничения:

* Router использует детерминированные правила;
* количество специализированных агентов ограничено двумя;
* база RAG содержит небольшой набор учебных материалов;
* SQLite используется как простое локальное хранилище;
* benchmark содержит небольшую тестовую выборку;
* качество моделей оценивается на ограниченном наборе сценариев.

Эти ограничения приняты для создания компактного локального прототипа.

---

## 17. Критерии готовности

Система считается готовой к демонстрации, если выполняются следующие условия:

1. Docker Compose успешно запускает все сервисы.
2. Orchestrator принимает пользовательский запрос.
3. Router выбирает соответствующего агента.
4. Tutor может объяснять понятия.
5. Assessment может генерировать задания.
6. Assessment может проверять ответы.
7. RAG возвращает учебный контекст.
8. Tools выполняют математические операции.
9. Memory сохраняет историю студента.
10. Tutor может использовать память, записанную Assessment.
11. Langfuse получает данные о выполнении запросов.
12. Три локальные модели протестированы benchmark.
13. Архитектура и результаты описаны в документации.

---
